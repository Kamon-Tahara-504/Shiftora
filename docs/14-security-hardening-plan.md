# 14. Security Hardening Plan (API実装と分離)

このドキュメントは、Shiftora を外部攻撃から守るための実装計画を整理する。
認証・業務APIの機能実装とは分離し、セキュリティ強化を独立して進める。

## 目的

- 外部攻撃（認証突破、セッション奪取、情報漏えい、DoS、権限昇格）への耐性を上げる
- 事故発生時の検知・追跡・封じ込めを可能にする
- セキュリティ要件をコードに継続的に組み込める状態にする

## スコープ

- 対象
  - フロントエンド（Next.js）
  - バックエンド（FastAPI）
  - Supabase 連携
  - デプロイ設定と運用監視
- 非対象
  - 業務機能の新規追加
  - 通常の API 機能拡張

## 脅威モデル（優先度順）

1. 認証・認可の欠陥（IDOR、権限チェック漏れ）
2. トークン漏えい（XSS、ログ出力、URL混入）
3. 入力値悪用（SQLi 相当、NoSQL 風注入、テンプレート注入）
4. CSRF / CORS 設定不備
5. ブルートフォース / クレデンシャルスタッフィング
6. 依存パッケージ脆弱性
7. 監査ログ不足による検知遅延

## 実装方針

### 1) 認証・セッション防御

- Access/Refresh トークンのライフタイムを明確化し、短命化
- Refresh ローテーションと失効処理を厳密化
- パスワード/トークンを URL・ログ・例外に出力しない
- 401 時の再発行フローを統一実装（多重リトライ抑止）

### 2) 入力検証と出力制御

- すべての write API で Pydantic バリデーションを厳格化
- 文字列長、文字種、許可値、null 許容を明示
- フロント入力値は trust せず、サーバで再検証
- エラーメッセージは情報漏えいしない内容へ統一

### 3) 認可境界の明確化

- org_admin / staff の権限制御をルーター単位で棚卸し
- 「他組織データ参照不可」を自動テストで固定化
- 重要操作（招待、シフト生成、権限変更）は監査ログ必須

### 4) Webアプリ防御ヘッダ

- CSP（段階導入: Report-Only -> Enforce）
- HSTS（本番のみ）
- X-Frame-Options / frame-ancestors
- X-Content-Type-Options, Referrer-Policy

### 5) レート制限と異常検知

- `/auth/login`, `/auth/refresh`, `/auth/signup`, `/auth/register-org` にレート制限
- IP 単位 + アカウント単位の複合制限
- 連続失敗閾値超過で一時ブロック + 監査イベント

### 6) 依存関係とサプライチェーン

- Python / Node の脆弱性スキャンを CI に組み込み
- lockfile 管理と定期アップデート運用
- 高リスク脆弱性（Critical/High）はマージブロック

### 7) ログ/監査/秘密情報管理

- 構造化ログ化（request_id, actor_id, org_id, action, result）
- 機微情報のマスキング（email 部分、token 全文禁止）
- `.env` 管理ルールの明文化とキーのローテーション手順化

## 実装フェーズ

### Phase 1: 即時対応（1-2日）

- パスワード/トークンの URL 混入防止（フォーム submit を POST + JS 送信へ統一）
- 監査ログの最低限強化（認証系イベント）
- API エラー応答の情報露出抑制

### Phase 2: 高優先防御（3-5日）

- 認可チェック棚卸しと不足修正
- レート制限導入
- セキュアヘッダ導入（まず Report-Only）

### Phase 3: 継続運用（継続）

- CI 脆弱性スキャン運用
- セキュリティテスト（回帰）を定期実行
- インシデント対応手順の更新

## 受け入れ基準

- 認証系エンドポイントでブルートフォース耐性がある
- 他組織データへアクセスできないことを自動テストで保証
- 機微情報が URL・ログに含まれない
- セキュリティヘッダと CORS が意図通りに適用される
- 脆弱性スキャン結果が CI で可視化される

## API実装との分離ルール

- セキュリティ強化は専用タスク/専用コミットで実施する
- 業務 API 機能追加 PR に混在させない
- レビュー観点を分離する（機能レビュー vs セキュリティレビュー）
